# Validation: how it works and what it cannot do

`python -m binproof validate <export-dir> -r result.json` checks an AI analysis against the data extracted from the
binary. It makes **no model call**. This page describes the three layers, the statuses, the test results and, most
importantly, the current limitations.

## The three layers (kept separate in every report)

| Layer | Question | Module | Reported as |
|---|---|---|---|
| 1. Evidence | Does each cited address / instruction / call / string / import / xref / code fragment exist, belong to this function, and match its quote? Is the quote specific enough to mean anything? | `validation/evidence.py` | `evidence[].status`, `evidence_status` |
| 2. Claim support | Do the claim's own specifics (numbers, quoted text, function names, caller/callee statements) stand on *verified* evidence and on the real call data? | `validation/support.py` | `findings[]` |
| 3. Semantic | Does the evidence actually *mean* what the claim says? | `validation/semantic.py` (interface only) | `semantic` |

`status` is the worst of the three. A favourable layer-3 verdict can never upgrade a claim that layers 1 or 2 flagged.
Layer 3 is not implemented yet: `RecordValidator(analysis, semantic_verifier=...)` is the plug-in point.

## Statuses

| Status | Meaning |
|---|---|
| `VERIFIED` | Every cited item exists, matches the data, and passed the grounding checks. **Not** proof the claim is true. |
| `PARTIALLY_VERIFIED` | Some evidence is weak or invalid, or the claim states specifics its verified evidence does not cover. |
| `UNVERIFIED` | No evidence, or none of it could be checked with the available data. |
| `INVALID_EVIDENCE` | Every cited item is missing or contradicts the data. |
| `CONTRADICTED` | The extracted data actively refutes the claim (for example "calls strcpy" when it does not). |

Exit codes of `validate`: `0` report produced, `1` a claim reached the `--fail-on` threshold, `2` error (bad input),
`3` **integrity failure**: the result's binary hash does not match the export (always, whatever `--fail-on` says).

## Integrity checks

* **Binary hash:** the result's `program_sha256` must equal the export's. A mismatch sets `integrity.ok = false`,
  prints an integrity failure and exits 3. A hash missing on either side is reported as *unknown*, not as a failure.
* **Context reproduction:** the exact model input is rebuilt from the export and compared with the hash stored in the
  result. `false` means the export changed since the analysis, non-default `--max-instructions` was used, or the
  context builder changed. It is a warning: evidence is then checked against the current export.
* Function name changes between analysis and export are noted.

## Decompiled-code evidence

Ghidra gives decompiled C no addresses, so decompiled evidence reports coordinates instead: the **line number(s)**,
how many times the quote **occurs** (ambiguity is reported, not guessed away), and the **corroborating assembly**
(instructions with the same constants, call sites to the same callees). Assembly cited as decompiled code is flagged
`wrong_evidence_kind`. Bare identifiers and very short fragments count as weak evidence.

## Weaknesses found while hardening (all fixed unless marked)

Found by attacking the first version with adversarial results. Before the fixes it marked 11 of 14 probes `VERIFIED`.

| Weakness | Fix |
|---|---|
| Real but irrelevant evidence (`PUSH RBP`) made a claim about `strlen` and 16 `VERIFIED` | claims whose specifics appear in none of their verified evidence are `PARTIALLY_VERIFIED`; prologue/epilogue-only evidence is flagged |
| Evidence swapped between claims passed | same relevance rule |
| The model's own `note` text and quotes from *invalid* evidence could ground a fabricated constant | grounding uses verified evidence only, never notes |
| Fabricated function names (`calls decryptPayload()`) were ignored | unknown identifier-like callees are `CONTRADICTED` |
| Internal names written plainly ("delegates to copyHelper") were ignored | more verbs, identifier-shaped names detected |
| "Does not call strcpy" was wrongly `CONTRADICTED` | negation handling (and "never calls strlen" is now correctly refuted) |
| `CMP`, `RAX`, `sVar1` counted as confirmations | minimum quote strengths |
| Decompiled evidence had no location; assembly cited as C got a bare "not found" | line numbers, occurrence counts, corroborating assembly, kind redirect |
| The same evidence cited three times counted three times | counted once |
| Binary hash mismatch still printed all `VERIFIED` and exited 0 | `integrity.ok`, exit code 3 |
| xref check accepted any quote containing the function's own name; metadata check accepted short numbers | tightened |
| Claim that reverses the real logic with real evidence passes | **not fixable deterministically** (limitation 1) |

## Current limitations

1. **Meaning is not checked.** A claim that reverses the logic ("returns 0xffffffff when valid"), inverts a condition,
   or is vague ("robust cryptographic validation") passes if its evidence is real, non-boilerplate and mentions the
   claim's constants. Needs the semantic layer (`limit-1..3` in the matrix).
2. **Claim-text checks are English-language heuristics.** They recognise a fixed set of verbs (calls, invokes,
   delegates to, forwards to, dispatches to, hands off to; called by/from) and a 24-character negation window. Other
   phrasing ("relies on", "passes the buffer to") is not checked. Plain lowercase names ("calls malloc", "calls the
   helper") are deliberately not flagged as unknown functions, because they cannot be told apart from ordinary words.
3. **Constants.** Every number in a claim must appear in verified evidence or in the function's code; numbers used in
   another sense (a count, "step 3") can produce a `weak` finding. Matching is lenient across sign and 32/64-bit
   forms (1 matches -1; -1 matches 0xffffffff), and the trivial values 0 and 1 are weak anchors.
4. **Partial coverage passes.** The relevance rule only fires when *none* of a claim's specifics are covered; if one is
   covered and others are not, the others get an informational `constant_not_cited`.
5. **No claim/evidence alignment.** For multi-part claims the validator cannot tell which evidence supports which part.
6. **Calls are direct calls only.** Indirect calls Ghidra could not resolve and truncated exports turn contradictions
   into `weak` warnings. Callers are only known from functions that were exported.
7. **Decompiled-code corroboration is heuristic.** It matches constants (ignoring 0 and +-1) and callee names, lists at
   most 8 addresses, and common constants can match unrelated instructions. Quote matching ignores whitespace, which can
   in rare cases join tokens across a boundary.
8. **Model notes are never verified,** not even for consistency with their own evidence.
9. **Strings** are only those Ghidra defined; stack or encoded strings are invisible. `referenced_from` is capped at 50
   per string, which yields `partial`, not `confirmed`, for heavily used strings.
10. **Single-function scope.** Claims about what a callee does are not validated.
11. **Integrity depends on the export.** A missing hash means "unknown". Context reproduction legitimately fails
    after any change to the context builder, so old results may show "not reproduced" after an upgrade.
12. **Test fixture.** `tests/checkserial_fixture.py` is a reconstruction of the real export (the golden test shows it
    agrees with the real run). No other real binary is in the suite yet.
13. **The overconfidence flag** compares claimed confidence with the final status. It does not measure calibration.
